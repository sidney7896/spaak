# Template update path

Record the current template version in the manifest. To update, compare a fresh generated project with the existing project, review migrations and contracts, apply compatible changes deliberately, and rerun all release gates. Template copying never overwrites an existing project.

Adoption preserves project identity. `.project-launch-starter.json` records the canonical slug, client and topology; rerunning the generator over an existing project with a different slug, client or topology is refused instead of leaving the manifest, profile, `.env.example`, docs and rendered migration disagreeing. Adopting across template versions is allowed and prints a notice naming both versions; the identity-bearing `.env.example` settings are rewritten on every run.

A launch manifest that does not record all three identity fields is refused as well, with or without a change: an unreadable identity is not an absent one. This matters because not everything is rebound on adoption. `docs/graduation.md` is rendered on **first generation only** — template copying never overwrites an existing file, and its placeholders are gone after the first run — so a partial rebinding would leave that one document naming the previous project's slug, topology and schema names while everything else moved. If you must change a project's identity, generate into a new directory.

`.project-launch-starter.json` also records `releaseControlsSha256`, the digest of the release controls this project was delivered with (`ops/release/workflow-templates.sha256` and `ops/release/global-policy.yaml`). It is recomputed on every generator run, and `ops/release/validate-workflows.mjs` checks it, so editing a delivered control without regenerating fails the workflow-validation gate.

Adoption by an **older** starter changes nothing and says so: the recorded version stays where it is, no file is overwritten, and the run does not offer the older starter as an available upgrade.

The recorded template version describes the files that are present, not the starter that ran. Because template copying never overwrites an existing file, an adoption by a newer starter adds only the files this project was missing: `source.template_version` in `PROJECT_MANIFEST.yaml` and `templateVersion` in `.project-launch-starter.json` therefore stay at the version the tree actually holds, and the newer one is recorded as `source.template_version_available` / `availableTemplateVersion`. `source.template_version` is a registry column and part of the project snapshot, so it must never claim a version the tree does not contain. To move a project to a newer template, compare it against a freshly generated project, apply the differences deliberately, rerun the gates, and only then record the new version.
